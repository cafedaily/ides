## 1. 这个目录是什么

代码告诉你**现在是什么样**，git log 告诉你**怎么走到这一步**。
`.structure/` 告诉你剩下的所有东西：

- **为什么**选了这条路
- **什么和什么**必须一起改（改了一个忘了另一个就是 bug）
- **哪些事**知道该做但还没做
- **上一轮**改了什么、测试过没过
- 项目各部分的**健康状态**

它不是给最终用户看的文档。它是给**接手代码的人**看的——
不管是你三个月后的自己，还是帮你写代码的 AI。

**核心原则：只写从代码和 git 里读不出来的东西。**

## 2. 快速上手

### 第一次看这个项目？

```
1. 读 .structure/overview.md        → 项目是什么
2. 读 .structure/tree.md            → 有哪些模块、什么状态
3. 读 .structure/debts.md           → 已知问题
4. 读 .structure/coupling.md        → 不能单独改的地方
```

四个文件，五分钟，你就知道这个项目的全貌了。

### 要改某个模块？

```
1. tree.md 找到模块 → 看状态标记
2. 进入那个目录的 .structure/STATUS.md → 看边界、当前真相、不要假设
3. 看 coupling.md → 这个改动会不会连锁影响
4. 开始改代码
```

### 改完之后？

```
1. 跑测试
2. 写 changelog（见第 8 节）
3. 更新 tree.md 里受影响模块的状态标记
4. 更新 STATUS.md 里的「当前真相」
5. 和代码一起 git commit
```

## 3. 目录结构

```
project/
├── .structure/                    项目级状态
│   ├── STRUCTURE.md                  本手册（人读）
│   ├── AGENT.md                      AI 智能体协议（机器读）
│   ├── INDEX.md                      入口目录
│   ├── tree.md                       模块树 + 状态标记
│   ├── overview.md                   项目概况
│   ├── files.md                      文件清单
│   ├── dataflow.md                   数据流
│   ├── coupling.md                   耦合关系（红线/黄线）
│   ├── api.md                        HTTP 接口
│   ├── debts.md                      已知欠账
│   ├── tests.md                      测试状态
│   ├── changelog/                    变更日志
│   │   ├── 2026-09-09_entity-layer.md
│   │   └── 2026-09-11_llm-chat-proxy.md
│   └── tasks/                        任务队列
│       └── BACKLOG.md
│
├── yang/.structure/               后端子模块状态
│   └── STATUS.md
├── web/.structure/                前端子模块状态
│   └── STATUS.md
└── tests/.structure/              测试子模块状态
    └── STATUS.md
```

### 层级关系

| 层级 | 位置 | 你应该什么时候读 |
|:---:|---|---|
| L0 | `.structure/` | 进项目第一件事 |
| L1 | `模块/.structure/` | 要改这个模块时 |
| L2 | `模块/子模块/.structure/` | 模块很大、有独立生命周期时才建 |

**不要一次读完所有文件。** tree.md 是目录，STATUS.md 是正文——
你不会一口气读完整本书，只翻你需要的那一章。

## 4. 核心文件说明

### tree.md — 模块地图

一屏看完项目全貌。每个模块一行，包含：
- 名字和文件列表
- 状态标记（✅🔧⚠️🆕💀）
- 依赖关系
- 上次变更时间

**维护节奏**：模块状态有变就更新。

### coupling.md — 危险关系

写清楚**改 A 必须同时改 B** 的所有情况。分两级：
- **红线**：不同步就会出 bug（有测试守着）
- **黄线**：最好一起检查（没测试守，靠人注意）

**这是这个目录里最重要的文件之一。** 大部分 bug 不是因为改错了，
而是因为改了一个地方忘了另一个。

### debts.md — 欠账清单

每条欠账包含：问题是什么、影响什么、怎么还。
比 TODO 注释好的地方是：所有欠账集中在一个文件里，不会散落在代码各处。

### STATUS.md — 子模块名片

每个子模块的 `.structure/STATUS.md` 是那个模块的「名片」：

- **是什么**：一两句话
- **边界**：做什么、**不做什么**（后者更重要——防止范围蔓延）
- **当前真相**：可以跑的验证命令，不确定时跑一下
- **不要假设**：过去犯过的错，防止重蹈覆辙
- **内部结构**：文件列表
- **依赖**：上下游关系
- **生命周期**：关键事件时间线

## 5. 子模块状态

当前项目有三个 L1 子模块：

| 模块 | 路径 | 职责 |
|---|---|---|
| 后端 | `yang/.structure/STATUS.md` | 算法、存储、HTTP、LLM 代理 |
| 前端 | `web/.structure/STATUS.md` | UI、离线存储、智能体调用 |
| 测试 | `tests/.structure/STATUS.md` | 94 条测试、跨语言对照 |

### 什么时候建新的子模块 STATUS.md？

当一个目录满足以下**任意两条**：
- 有独立的生命周期（被独立开发/测试/部署）
- 有清晰的边界（做 X 不做 Y）
- 代码量超过 500 行
- 有独立的依赖关系

不要过度拆分——三到五个 L1 子模块是大多数项目的甜点。

## 6. 日常工作流

### 开始一天的工作

```
git pull
看 .structure/tasks/BACKLOG.md → 最高优先级是什么
看 tree.md → 相关模块什么状态
开始写代码
```

### 做完一个改动

```
跑测试 → 确认全过
写 changelog/YYYY-MM-DD_{slug}.md
更新 tree.md（状态标记）
更新受影响模块的 STATUS.md（当前真相）
更新 BACKLOG.md（完成/新增任务）
如果有新欠账 → 更新 debts.md
git add . && git commit
```

### 发现了一个新坑但现在不修

```
写入 debts.md → 问题/影响/怎么还
如果影响够大 → 在 BACKLOG.md 建任务
继续手上的工作
```

## 7. 状态标记定义

| 标记 | 含义 | 改之前该做什么 |
|:---:|---|---|
| ✅ | 稳定，测试覆盖充分 | 先跑测试 |
| 🔧 | 开发中，可能有未完成部分 | 先读最近的 changelog |
| ⚠️ | 有已知问题（见 debts.md） | 改时注意不加重 |
| 🆕 | 新建，没经过真实使用 | 先写测试再改逻辑 |
| 💀 | 废弃，等删 | 不要在上面建东西 |

### 状态流转

```
🆕 新建 → 🔧 开发中 → ✅ 稳定
                ↓
               ⚠️ 有问题 → 🔧 修复中 → ✅
                                         ↓
                                        💀 废弃
```

## 8. 变更日志写法

### 文件位置

```
.structure/changelog/YYYY-MM-DD_{slug}.md
```

同一天多轮加序号：`2026-09-11_01_xxx.md`

### 模板

```markdown
# {标题}

- **日期**: YYYY-MM-DD
- **触发**: 为什么做这个改动

## 做了什么

- 列表形式，每条一个改动

## 测试

改动前：X pass / Y fail / Z skip
改动后：X pass / Y fail / Z skip

## 影响了哪些模块

- 后端/接口: 🆕 → 🔧

## 遗留

- 发现的新欠账
```

### 写作原则

1. **只写结果，不写过程**。不要写「先试了 A 不行然后试了 B」。
2. **测试状态必须写**。
3. **一轮改动一条**。多个 commit 合并。
4. **和代码一起 commit**。

## 9. 任务队列管理

### 文件位置

```
.structure/tasks/BACKLOG.md
```

### 优先级

| 级别 | 含义 | 例子 |
|:---:|---|---|
| P0 | 阻塞：测试挂了、服务起不来 | 「import 报错」 |
| P1 | 影响体验或安全 | 「接口没认证」 |
| P2 | 正常迭代 | 「加流式支持」 |
| P3 | 有空再说 | 「嵌入模型」 |

### 管理原则

- 新任务默认 P2，除非明显是 P0/P1
- 完成的任务移到「已完成」区，带 changelog 链接
- 定期清理——超过一个月没动的 P3 考虑删掉

## 10. 防止信息腐烂

`.structure/` 最大的风险是写了没人维护，变成误导性的废文档。

### 防线

1. **和代码同 commit**。不是事后补的——是改动的一部分。
2. **可验证断言**。STATUS.md 的「当前真相」是可以跑的命令。跑一下就知道还准不准。
3. **不写从代码能读出来的东西**。代码变了不用同步。
4. **coupling.md 有测试守着**。红线耦合对应的测试挂了 → 说明耦合关系还在。
5. **changelog 只增不改**。历史记录不会过时，因为它描述的是过去。

### 腐烂信号

- tree.md 的「上次变更」和 git log 不一致
- STATUS.md 的「当前真相」跑不过
- debts.md 的「已解决」和代码对不上
- 超过三轮对话没有新 changelog

看到腐烂，优先修 `.structure/`——它的价值建立在准确之上。

## 11. 和 git 的关系

### .structure/ 入版本控制

```gitignore
# 不要 ignore .structure/
# 只 ignore 临时文件
.structure/tmp/
```

### 提交纪律

代码和 `.structure/` 在**同一个 commit** 里。

```bash
git add yang/chat.py .structure/
git commit -m "加 /api/chat LLM 代理"
```

### 回溯

checkout 任意历史 commit，`.structure/` 描述的就是**那个时刻**的项目状态。
这让 `git bisect` 不只能定位代码变更，还能定位**决策变更**。

## 12. 和 README 的关系

| | README.md | .structure/ |
|---|---|---|
| 读者 | 用户、评估者 | 开发者、AI |
| 内容 | 怎么用 | 怎么改 |
| 深度 | 表面 | 完整 |
| 更新频率 | 版本发布时 | 每次代码变更 |

两者不应该矛盾。冲突时以代码为准，两边都更新。

## 13. FAQ

### Q: 项目很小，需要 .structure/ 吗？

如果一个人能记住整个项目的状态，不需要。
但如果你用 AI 辅助开发，`.structure/` 就是 AI 的工作记忆——
它记不住上一轮对话的内容。

### Q: 和 ADR（Architecture Decision Records）有什么区别？

ADR 只记录决策。`.structure/` 还记录当前状态、耦合关系、任务队列。
changelog 的「关键决策」部分承担了 ADR 的角色。

### Q: 和 docs/ 目录有什么区别？

`docs/` 是给项目外部读者的文档。`.structure/` 是给项目内部开发者的状态。
两者的受众不同、更新节奏不同、信息密度不同。

### Q: STATUS.md 和代码注释的边界在哪？

代码注释解释单个函数/行的 what 和 why。
STATUS.md 解释整个模块的 what 和 what-not。
如果你在 STATUS.md 里写「第 42 行做了 X」，那它应该是代码注释。

### Q: changelog 写到什么粒度？

一条 changelog 对应**一轮工作**（可能包含多个 commit）。
粒度大约是「值得告诉接手人的一段改动」。
太细（「改了个 typo」）和太粗（「重构了整个后端」）都不好。
